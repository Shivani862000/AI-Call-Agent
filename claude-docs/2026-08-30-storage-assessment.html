AI-Call-Agent · storage assessment · branch vikrant-enhancements

Where the call data lands

Every completed call fans out into five stores with five different durability guarantees. One of them is the database everyone thinks about. The other four hold audio, transcripts, audit logs and live session state — and three of them do not survive a container restart.

01 · Topology

One call, five destinations

The write path is driven by three components, in order: the WebSocket media bridge while the caller is on the line, the post-call pipeline after hangup, and the scheduler that decides on retries. Each one writes to SQLite, and each one also writes somewhere SQLite does not reach.

02 · Primary store

SQLite is the whole database

There is no Postgres and no Redis in the running system, despite POSTGRES_URL and REDIS_URL sitting in .env.example. Nothing in the codebase reads either variable. Everything structured lives in one file — DATABASE_URL, defaulting to ./feedback.db, set to /app/data/feedback.db in production.

03 · The other four stores

What SQLite only keeps a pointer to

Each card below is a real store holding real call content. The badge is what actually happens to that data when the container is recreated — read from the compose files, the k8s manifests, and the code paths that write them.

Call audio — mixed WAV

Written
By the media bridge on socket close — 8 kHz mono PCM, caller and AI mixed into one track

Kubernetes sets RECORDINGS_DIR to the mounted volume. Neither compose file does, so under Docker Compose these land in /app/recordings, which is not a volume. The DB keeps the path; the audio is gone.

Provider recordings — downloaded MP3

Volume-mounted in both compose and k8s, so the bytes survive. But this path ignores RECORDINGS_DIR entirely, so the two recording stores can never be pointed at the same place. Nothing ever deletes from here.

Where patient data leaves the box

Storage is not only what you keep. Four external destinations receive data from this system, and only one of them is optional in practice.

The support-ticket path is the one that got privacy right. src/support-ticket.js strips emails, Indian mobile numbers, patient/DOB/diagnosis fields and API keys from the description, replaces the page title with a fixed route name, and drops query strings from the URL before anything is stored or sent. That discipline is not applied to the CRM webhook, which forwards name and phone in the clear.
05 · Findings

What I would fix, in order

Ranked by what breaks first at real volume. Each one was verified against the running database or the code path, not inferred from the schema.

Repeat callers silently become duplicate patient records

findCustomerByPhone() normalises the incoming number in JavaScript, then compares it against only the 200 most recently created customers. Past 200 records, an existing patient who calls back is not found, and ensureIncomingCustomerForCall() inserts a second row for them — splitting their call history and feedback across two IDs.

src/call-management.js:180 const customers = await dbAll('SELECT * FROM customers ORDER BY id DESC LIMIT 200'); return customers.find((c) => normalizePhoneLookupValue(c.phone) === normalized) || null;

This is not guarded by the schema either: migration_script.js deliberately rebuilt customers to drop the UNIQUE constraint on phone. And customers.normalized_phone exists as a column but is never written or read — the fix the schema was reaching for was never wired up.

Fix: populate normalized_phone on write, add a unique index on it, and make the lookup a single indexed query.

Every hot query is a full table scan

The database has exactly one non-key index, and it is on support_tickets. Meanwhile calls.customer_id, calls.provider_call_id, calls.call_id joins, feedback.customer_id and customers.phone are all queried by equality on every call and every dashboard load, unindexed.

sqlite_master indexes (non-auto): 1 support_tickets_status_updated_idx WHERE provider_call_id = ... 4 sites WHERE customer_id = ... 4 sites WHERE call_id = ... 5 sites WHERE phone = ... 5 sites

Fix: four indexes. calls(customer_id), calls(provider_call_id), feedback(customer_id), customers(normalized_phone).

Foreign keys are declared but not enforced

Five FOREIGN KEY clauses appear across calls, feedback, clients and call_supervisor_events. SQLite ignores all of them unless PRAGMA foreign_keys = ON is set per connection, and it never is. I confirmed this against the live database.

PRAGMA foreign_keys -> {"foreign_keys": 0}

The deletion routes compensate by hand-ordering deletes — routes/customers.js deletes feedback, then calls, then the customer — which works until someone adds a route that forgets. That scripts/check-integrity.js exists specifically to hunt for orphan rows is the tell.

Fix: enable the pragma on connect and add ON DELETE CASCADE, or drop the FK clauses so they stop implying a guarantee that isn't there.

Rollback journal, no busy timeout, concurrent writers

The database runs in journal_mode=delete with no busy_timeout configured. Three things write concurrently: the media bridge during a call, the post-call pipeline fired into the background via runInBackground, and the scheduler tick. Under rollback journalling a reader blocks a writer outright, and with no busy timeout the loser gets SQLITE_BUSY immediately rather than waiting.

PRAGMA journal_mode -> {"journal_mode": "delete"} PRAGMA busy_timeout -> never set

Fix: two lines at connect — PRAGMA journal_mode = WAL and PRAGMA busy_timeout = 5000. WAL lets readers and the writer proceed together, which is exactly this workload.

Call audio is orphaned by the compose deployment

The media bridge writes the mixed WAV to process.env.RECORDINGS_DIR, falling back to <cwd>/recordings. The k8s deployment sets that variable to the mounted path. Neither docker-compose.yml nor docker-compose.prod.yml sets it — they only mount /tmp/feedback-call-recordings, which is the other recording path, used by the download pipeline.

k8s/deployment.yaml:34 RECORDINGS_DIR: /tmp/feedback-call-recordings ✓ docker-compose.yml (not set) -> writes to /app/recordings ✗ docker-compose.prod.yml (not set) -> writes to /app/recordings ✗

The path is still stored in calls.recording_local_path, so playback fails only later, when someone tries to listen.

Fix: set RECORDINGS_DIR in both compose files, or better, make services/post-call-pipeline.js read the same variable instead of hardcoding /tmp.

No retention policy exists, on health data

customers.data_retention_until was added to the schema and has zero references anywhere in the codebase — nothing writes it, nothing reads it, no job acts on it. dnd_checked_at has one. There is no purge path of any kind.

What accumulates indefinitely: full call transcripts, AI analysis of those transcripts, sentiment scores, mixed-audio recordings of both parties, patient dates of birth and treatment types in clients. The only deletion available is manual and total — DELETE /api/customers/bulk and DELETE /api/calls/bulk wipe everything.

Fix: decide a retention window, write data_retention_until at customer creation, and add a scheduler tick that deletes expired rows and their recording files. The recording deletion is the part that gets forgotten.

Credentials are hardcoded in the migration, and one of them deletes yours

db.js upserts three named accounts with committed bcrypt hashes on every single boot, then runs a cleanup line that deletes any user named admin or agent1.

db.js:247-261 INSERT ... ['admin@vikitechsolutions.in', '$2b$10$QlPAd0...'] INSERT ... ['agent1@vikitechsolutions.in', '$2b$10$Qy6oQI...'] INSERT ... ['PRASHANTGUPTA74@YAHOO.CO.UK', '$2b$10$pMFMyP...'] DELETE FROM users WHERE username IN ('admin', 'agent1')

Because .env.example ships ADMIN_USERNAME=admin, following the README produces an admin account that is created and then deleted in the same transaction — which is why local login fails until you rename the user. The upsert also means an operator cannot rotate those three passwords: the next restart resets them.

It also breaks the test suite. test/database-safety.test.js asserts on the user table and fails because of these three rows — 49 of 50 tests pass.

Fix: delete the three hardcoded inserts and the cleanup line; bootstrap from ADMIN_USERNAME / ADMIN_PASSWORD_HASH only, and only when the table is empty.

The audit log has nowhere durable to live

logs/system.log records logins, call outcomes and bulk deletions, and the redaction in services/system-logger.js is genuinely careful. But no volume or mount in any deployment file points at that directory, so the file is inside the container's writable layer and disappears with the container.

The admin UI reads it back through /api/logs, so operators see a log that appears complete and is simply missing everything before the last redeploy.

Fix: mount it, or set SYSTEM_LOG_DIR to a path inside /app/data which is already persistent.

Schema only grows — 74 columns, many of them dead

Migrations are a linear list of addColumnIfMissing() calls with no version table, no down path, and no way to remove a column. calls has reached 74 columns and customers 51. A grep for each column name across src, services, routes, public and scripts finds these referenced nowhere but the migration itself:

customers data_retention_until, normalized_phone, phone_number, scheduled_at, last_attempt_at, next_attempt_at, last_pickup_slot, provider_request_id calls scheduled_at, uuid, invoice_triggered, proposal_triggered, recording_consent_captured, recording_download_status, supervisor_notes, call_end_reason

There are also three overlapping pairs left behind by the growth: status/outcome (kept in sync by a trigger), sentiment/sentiment_label, and analysis_summary/summary.

Fix: add a schema_migrations table before the column count makes any cleanup unsafe to attempt.

Two dead paths worth knowing about

The owner digest is never delivered. runOwnerDigestTick() builds the full digest text into a local lines variable, never sends it anywhere, and then writes owner_morning_digest_last_sent to app_state and logs "Morning digest sent successfully". The only thing app_state stores is a marker for a message nobody receives.

The demo seed script is broken. scripts/seed-demo-reports.js inserts into calls.whatsapp_summary_sent, a column that no longer exists. It fails partway with no transaction wrapping it — running it on my clean database left 12 customers and 12 clients with zero calls and zero feedback.

$ node scripts/seed-demo-reports.js Error: SQLITE_ERROR: table calls has no column named whatsapp_summary_sent customers 12 calls 0 clients 12 feedback 0

Fix: either send the digest or delete the tick; wrap the seed in a transaction and drop the stale column.

06 · Method

How this was verified

  • The app was booted locally and driven through the browser: login, dashboard, support tickets. A customer and a manual feedback row were created through the API and read back out of the SQLite file to confirm the write path end to end.
  • Schema facts come from PRAGMA table_info and sqlite_master on the live feedback.db, not from reading the migration — which matters, because the migration and the actual schema have already diverged.
  • PRAGMA foreign_keys and PRAGMA journal_mode were queried at runtime.
  • Dead columns were identified by whole-word grep of every column name across src, services, routes, public and scripts.
  • npm test was run: 49 of 50 pass. scripts/check-integrity.js passes all three checks on this dataset, which is expected — the data is too small for the 200-row lookup window to have caused a duplicate yet.
One correction to an earlier note. I flagged /reports.html returning 404 as a possible routing gap. It is not — index.js:104 disables it deliberately, alongside /incoming-calls.html, and routes/reports.js is an intentionally empty router. The dead weight left behind is services/pdf.js and services/reporting.js, which still write PDFs to /tmp that nothing cleans up.
