# P04 Complete Route, Session and Database Access Boundaries

**Goal:** Every actual route observes its intended role, AGENT responses exclude restricted data, logout remains effective after restart, and the queue view cannot expose protected rows through a browser database role.
**Spec:** [P04 contract](../2026-09-08-APPLICATION_GAP_REMEDIATION_PLAN.md#p04--bind-authorization-to-actual-routes-and-shape-sensitive-responses) and [working access policy](../APPLICATION_DOMAIN_CONTRACTS.md).
**Dependencies:** reviewed P01/P07 and prior P00a/P04 fixes. Task 2 also requires P03's schema contract/recovery implementation. Record actual prerequisite commits at dispatch.

## Global Constraints

- Current remediation checkout, existing custom migrations and tested authorization behavior. No live database/provider/notification/host operation, push, merge or deployment.
- Reuse actual Express routes/auth and the guarded disposable database. Synthetic users, passwords and patient sentinels only; no real configuration files. External service boundaries remain inert.
- AGENT retains permitted operational workflows and masked contact labels. Recordings, transcripts, analysis/PDF and supervisor payloads remain ADMIN-only, including nested/inline copies. Patient creation with an already-known contact remains permitted; saved-contact editing is ADMIN-only.
- The current session lifetime is 12 hours and account-state cache bound is 30 seconds. Local account mutations invalidate immediately. State explicitly what a copied session can do after logout/password change/restart; clearing one browser cookie is not durable revocation.
- Task 1 is schema-free at `0019`. Task 2 uses the reserved append-only `0020_access_boundaries.sql`; lifecycle migrations are now planned at `0021`–`0024` in the main manifest. Confirm no intervening migration before dispatch; never reuse or modify a distributed migration.

### Task 1: Finish actual-router and response coverage

1. Inventory the mounted routes/methods and numeric versus string identifier parameters from actual source. Retain P00a's full-path guards. Add deliberate authorization to independently mountable sensitive routers so mounting one without the outer app does not silently make it public. Do not apply numeric validation to intentional string keys.
2. Reproduce invalid/padded/signed/overflow ID dispatch and any missing role boundary with actual HTTP requests. Validate canonical positive safe-integer IDs before a data query/write, after required role denial. Cover each router family and sensitive verb, casing, trailing/repeated slashes, percent encodings and raw dot-segment request targets. A client that normalizes the path before sending does not test the latter.
3. Replace AGENT patient/queue response object spreads with explicit permitted fields. Remove raw contact aliases, nested arbitrary payloads and contact-bearing unrestricted notes/analysis copies; keep useful fixed operational enums, dates, flags and masked labels. ADMIN retains authorized detail. Apply shaping to list/search/detail and mutation responses; add sentinels through actual routes, including queue/patient joins. Adapt the affected UI so omitted restricted fields are not resubmitted as clears.
4. Use seeded real users and signed cookies to test login, current-session inspection, demotion, deactivation, deletion, password change/reset and auth lookup failure. Verify the defined cache bound with controlled time and separate process/cache contexts. Denied requests must not reach mutation/provider/storage spies. Include valid authorized workflows and another user's resource/token where relevant.
5. Inspect the same-millisecond/one-second password timestamp boundary: the current `pwd + 1000` tolerance can accept an older token after a rapid password reset. Add a failing behavioral case and correct the schema-free precision behavior where possible; Task 2's durable credential revision supplies the final race-free contract. Do not claim full password/session assurance while that gate is open.
6. Run affected isolated HTTP/DB and existing remediation tests; record bounded coverage, update this plan and commit only named task files. Controller performs independent review before Task 2.

### Task 2: Add durable session revocation and close the view boundary

1. After P03 readiness, create `0020_access_boundaries.sql` with durable user credential revision and session revocation storage. Existing valid sessions need an explicit finite compatibility rule. Store opaque hashes/IDs and expiry, never raw cookies/passwords; processing/revocation storage must not be exposed through the Data API. Keep cleanup bounded. Apply RLS and reviewed grants to any exposed-schema table.
2. Bind new tokens to the stored credential revision. Increment the revision atomically on password change/reset so even changes within one millisecond revoke older credentials; do not rely on timestamp tolerance. Persist logout revocation before reporting success and clearing the cookie. Check revocation in authentication with the declared bound, fail closed on lookup errors, and prove it survives app restart. Do not revoke unrelated sessions through an undocumented side effect.
3. Preserve the existing `customer_queue` definition/columns and writable trigger behavior while setting `security_invoker = true`. Revoke browser-role access that the application architecture does not expose; retain only the trusted server grants needed for actual routes. Inventory other application views/functions and their grants for equivalent leaks. Do not edit `0019` or conceal the finding by changing only a fixture.
4. For permission rehearsal, create the relevant named Supabase-equivalent roles and representative prior default grants **before** applying the new migration. Verify the migration's resulting privileges using existing patient/queue sentinels. Do not re-grant away the policy after migration or use only an empty table. Browser access must fail/return no protected rows while the trusted server can perform supported queue reads/writes. Record remaining differences from managed Supabase rather than claiming equivalence from role names.
5. Regress copied-cookie replay after logout and process restart, same-instant credential reset, inactive/deleted/demoted accounts, old-token compatibility expiry, DB errors, valid new login and concurrent logout/use within the declared bound. Test all direct `pg` clients with purpose-bound guards before construction. Rehearse fresh install and nonempty upgrade using the P03 schema contract, with no unexpected skips.
6. Document the exact credential/session compatibility and browser database policy, run affected auth/route/schema tests, and commit named migration/application/test changes together. Actual deployed privilege inspection, hosted CI and authenticated browser tests remain separately recorded evidence until run.

Implementation reference checked 9 September: [Supabase views and RLS](https://supabase.com/docs/guides/database/postgres/row-level-security#views-and-rls) explains the default owner-permission issue; [PostgreSQL 17 CREATE VIEW](https://www.postgresql.org/docs/17/sql-createview.html) defines caller-permission behavior for `security_invoker`. These support the proposed migration; they do not establish the current projects' effective grants.

Rollback: schema-free code can be reverted independently. The access expansion uses P03's tested schema/image compatibility path; never restore browser grants or disable revocation to make a stale build appear healthy. A rollback that restores an exposure is not a completed remediation.
