# P03 Targeted Releases and Schema Recovery

**Goal:** A release changes only the chosen environment and verifies database readiness and build identity, with an honest recovery path after schema changes.
**Spec:** [P03 contract](../2026-09-08-APPLICATION_GAP_REMEDIATION_PLAN.md#p03--isolate-releases-and-establish-schema-recovery).
**Dependencies:** reviewed P01; P06 sanitized production image for the full image rehearsal. P03a's disposable sibling-service rehearsal can start earlier. Record prerequisite commits at dispatch.

## Global Constraints

- Current remediation branch and existing custom migration authority; distributed migrations are immutable. This task does not deploy, push, contact a live host/database, copy secrets or alter provider configuration.
- Test only UUID-owned Docker/Compose resources and synthetic environment/configuration files. Reuse the P01 guarded DB identity for schema tests. Never run the old deploy script against an actual application host as a reproduction.
- Host interpolation config contains both required `PROD_APP_IMAGE` and `UAT_APP_IMAGE`, independently pinned; no shared `APP_IMAGE` fallback. Application secrets remain separate and are never printed by an effective-config check.
- Preserve registry authentication and `/opt/app` host working-directory semantics. The local rehearsal uses an explicitly supplied owned test directory, project name and synthetic credentials.
- One host lock governs shared configuration mutations; destination-environment workflow concurrency prevents overlapping releases. No proxy/dependency restart or image prune in an app release.

### Task 1: Replace the coupled release path

1. Add behavior tests for actual release command execution using a controlled command boundary and temporary host fixture. Reproduce shared image interpolation, sibling/proxy restart and stale 200 readiness acceptance without reaching a real host. Test missing/ambiguous target, missing pinned sibling config and unsafe config values before any mutation.
2. Change production Compose to independent required image values and independent environment credential mounts. Remove misleading claims that an environment name prevents a wrongly configured database URL. Version the Compose/proxy assets; calculate and verify a manifest digest before activation. Proxy activation is a separate explicit operation.
3. Replace the obsolete `app`/`nginx` script with the single supported `prod|uat` target runner. Under a shared host lock, validate saved config and selected image/build, preserve prior config/image, atomically update only the selected image key, then pull/up only that service using `--no-deps`. Preserve the sibling value and container/proxy identity. Trap failure without discarding recovery state; never print app env or registry tokens.
4. Replace automatic branch-push UAT deployment with explicit environment dispatch. Deliver verified versioned release assets to the host, retain registry login and working directory, and invoke the same runner. Serialize by destination environment; tests/builds remain independent. Remove the old login-page health loop and pruning. Do not execute this workflow externally.
5. Implement a bounded readiness probe: 180-second rollout deadline, two-second connection and five-second total probe limit. Require `/health` success plus the expected immutable build identity from a trusted local container/probe surface; an arbitrary 200 page or caller-supplied environment SHA is insufficient evidence of image contents. Public health must not disclose secrets.
6. Rehearse the real runner with actual owned Compose siblings and a synthetic proxy on an internal network. Inspect effective config safely and record target/sibling/proxy container IDs, image identities and isolated DB schema before/after. Exercise target update, stale-build 200, failed readiness, missing config, concurrent release serialization and target-only schema-free rollback. Remove only owned resources in `finally`, including failures.
7. Document required host config/bootstrap, credential separation, asset verification, recovery and proxy-change procedure in `claude-docs/DEPLOYMENT_AND_RECOVERY_RUNBOOK.md`; update README to one path. Record measured local timings and limitations, commit named files and obtain review before Task 2.

### Task 2: Verify the required migration set and recovery compatibility

1. Create `src/schema-contract.js` with an explicit immutable required migration identity set and declared supported schema bounds. Validate source filenames, duplicate versions and manifest mismatches before connecting or executing SQL. Maximum-version or `startsWith` checks alone are invalid. Preserve the P01 mandatory test guard and import-safe CLI.
2. Update `scripts/migrate.js`, application initialization and readiness to consume the same contract. Verify applied required versions/names and reject holes, unexpected incompatible future versions and conflicting identities. Preserve custom migration bookkeeping; do not silently reinterpret a Supabase-managed history record or introduce a second authority. Bound DB checks and close clients/return checked-out connections on every outcome. Do not log arbitrary migration SQL/driver messages containing data.
3. Use the guarded owner connection to test fresh install, nonempty `0019` upgrade, idempotent repeat, missing intermediate migration, duplicate local versions, applied identity mismatch, an incompatible future version and rollback of an injected failing intermediate migration. Assert exact committed set after failure; the previous image is not automatically declared compatible with a partially advanced schema.
4. Integrate explicit schema-free versus schema-changing release modes. Schema-changing releases require a captured recovery checkpoint and an explicitly verified compatible image contract; failure after migration enters a visible recovery-required state. Do not blindly restart the prior image, run destructive down migrations or promise data restoration without tested evidence.
5. Rehearse DB outage, query timeout, schema changed under a running app, failed intermediate migration, restart and compatible/incompatible previous-image recovery using owned resources. Record image/schema identities, retained writes and timing. Supply bounded read-only inventory/rehearsal tooling and an evidence template for actual production volume, duplicates, table/index bytes and checkpoint/restore evidence; unavailable live evidence remains a release gate.
6. Run affected isolated schema/release tests and existing DB initialization/health regressions. Update the runbook, Tier2 evidence and named-files commit. Main-plan/evidence updates and separate review belong to the controller.

Rollback: Task 1 can restore the prior selected image/config for a proven unchanged schema while keeping the sibling/proxy untouched. Task 2 follows the verified schema compatibility contract: forward fix or an explicitly authorized restore when old-image compatibility is unproved. No destructive recovery action is part of local implementation.
